# Harness 项目规则说明（人读版）

## 🚀 在新项目中接入 harness

> 把 `.harness/` 整个目录拷到目标项目根，推荐先探测再起草规则。

### Agent 起草链路（推荐，更准确）

```bash
# 1. 只读探测 facts
.harness/commands/harness probe --json > /tmp/harness-probe.json

# 2. Agent 根据 facts 起草 rules.yaml（不确定的层归属必须先问用户）

# 3. 写入规则
.harness/commands/harness init --rules /tmp/harness-rules.yaml

# 4. 安装 Agent hook + 扫描
.harness/commands/harness install --agent claude   # 或 ducc / baidu-cc
.harness/commands/harness scan
```

### 快速接入（旧链路，适合标准结构新项目）

```bash
# 一键接入：内部按序跑 init --yes + install + scan
.harness/commands/harness setup --agent claude       # 或 ducc / baidu-cc
```

`setup` 等价于下面三步，但**对所有 conflict 走默认值，无交互**：

```bash
.harness/commands/harness init --yes
.harness/commands/harness install --agent claude
.harness/commands/harness scan
```

### 想看探测细节 / 手动选 conflict？

用 `--interactive` 让 init 阶段弹问题让你选；或者拆成原始三步逐个跑：

```bash
.harness/commands/harness setup --agent claude --interactive   # init 走交互
# 或
.harness/commands/harness init               # 完全交互
.harness/commands/harness init --dry-run     # 只看 plan 不写盘
.harness/commands/harness init --json        # CI / 程序消费用
```

### 老项目接入（务实派）

老项目的存量违规通常**不敢碰**——动一行可能炸一片。建议先完成接入和 baseline，再决定是否只管增量：

```bash
# 1) 先关闭治理，避免规则未对齐时误拦截
.harness/commands/harness mode off

# 2) 只读探测 facts，交给 Agent 起草 rules.yaml
.harness/commands/harness probe --json > /tmp/harness-probe.json
.harness/commands/harness init --rules /tmp/harness-rules.yaml

# 3) 安装 hook + 扫描
.harness/commands/harness install --agent claude
.harness/commands/harness scan
.harness/commands/harness doctor
```

如果只想约束 Agent 后续改动，可以在规则对齐后切到 `strict`，但不强制一次性修完存量问题。想评估 baseline 时用：

```bash
.harness/commands/harness validate-all --json | python3 -m json.tool | head -40
.harness/commands/harness check --json | python3 -m json.tool | head -40
```

### init 三段式做了什么

`setup` 内部跑的 `init` 是三段式（probe → resolve → apply）：

| 阶段 | 干什么 | 产出 |
|------|--------|------|
| probe   | 只读扫一遍项目根：tsconfig.json / package.json / src/ / .eslintrc / .gitignore | `ProbeReport` |
| resolve | 对照出厂默认 `rules.yaml`，自动采纳能采纳的，分歧抛 `Conflict` 让用户选 | `ProposedPlan` |
| apply   | 把用户答复（或 `--yes` 走 `default_choice`）落到 rules.yaml + 必要目录 | 写盘 |

**自动采纳的**（不打扰用户）：
- tsconfig.json `paths` 别名（采纳探测值，与默认一致时静默沿用）
- layer 路径与默认不同时直接采纳现状（例：默认 `component.paths=[src/pages/, src/components/]`，但项目只有 `src/components/` → 采纳）
- 探测到的框架 / 包管理器（只打 info note，不进 rules）

**抛 conflict 让用户拍板的**（`--yes` / `setup` 默认走 default_choice）：
- `src/` 下未识别的目录（例 `src/utils/`）：映射到某 layer / 加进 `exclude_dirs` / 先放着
- 命名风格背离默认（样本 ≥ 3 且实际命中率 < 50%）：保留默认 / 采纳现状风格 / 不校验该层

**不会自动猜的**：
- `imports.forbidden_imports` / `imports.rewrites` —— 业务语义无法探测，需要手写

接入后建议看 [`.harness/docs/presets.md`](docs/presets.md) 对照常见项目形态调整。
